# Target Architecture Design

Issue: #29
Current status sync issue: #111
Parent epic: #23

This is the Phase 2 architecture plan for the React/FastAPI product rewrite. It
started as a design baseline. Some slices are now implemented; current phase
status and next issue selection live in
[product-refactor-status.md](product-refactor-status.md). Implementation PRs
should reference this document and keep business behavior parity with the golden
masters in `tests/fixtures/golden_master/`.

## Confirmed Stack

- Frontend: React + Vite + TypeScript.
- Backend: FastAPI.
- Core business logic: Python domain modules.
- Product-state database: SQLite.
- Analytical database: DuckDB.
- UI libraries: React Router, TanStack Query, TanStack Table, Apache ECharts,
  Tailwind CSS, shadcn/ui conventions, lucide-react.
- Backend libraries: Pydantic v2, SQLAlchemy 2.x, Alembic, DuckDB Python API,
  pytest, FastAPI TestClient or HTTPX.
- Product shape: local-first React web frontend plus FastAPI backend.
- Out of scope: simulated trading / paper trading, real broker integration,
  multi-user auth, cloud-only services.

## Repository Shape

The rewrite should introduce new product-owned areas without immediately
deleting legacy modules:

```text

    stocktrade_api/
      main.py
```

Legacy `pipeline/`, `agent/`, `dashboard/`, `workbench/`, and `data/` stay
available as oracle and migration sources until the relevant parity and cutover
PRs are merged.

## Boundary Rules

- `src/stocktrade/domain/` owns pure Python business behavior.
- `apps/api/stocktrade_api/routes/` owns HTTP only.
- `apps/api/stocktrade_api/services/` coordinates domain, jobs, storage, and
  external providers.
- `apps/api/stocktrade_api/jobs/` owns job lifecycle and cancellation.
- `apps/api/stocktrade_api/storage/` owns SQLite/DuckDB access.
- `apps/web/src/api/` owns typed API clients.
- `apps/web/src/features/` owns product workflow views.
- No domain rule should depend on React, FastAPI request objects, SQLAlchemy
  sessions, DuckDB connections, model calls, or filesystem paths.

## SQLite Ownership

SQLite stores product state and transactional metadata.

| Table | Purpose | Key Fields |
| --- | --- | --- |
| `schema_versions` | SQLite migration state | `component`, `version`, `applied_at` |
| `app_settings` | product settings | `key`, `value_json`, `updated_at` |
| `data_sources` | market/review provider config metadata | `id`, `kind`, `name`, `status`, `config_json` |
| `strategy_configs` | versioned strategy config snapshots | `id`, `name`, `version`, `config_json`, `created_at` |
| `runs` | user-visible workflow runs | `id`, `kind`, `status`, `pick_date`, `started_at`, `finished_at`, `summary_json` |
| `job_steps` | per-step status | `id`, `run_id`, `name`, `status`, `started_at`, `finished_at`, `error_json` |
| `job_events` | append-only event log index | `id`, `run_id`, `step_id`, `level`, `message`, `created_at` |
| `artifacts` | files generated by runs | `id`, `run_id`, `kind`, `path`, `content_type`, `metadata_json` |
| `candidate_batches` | candidate run header | `id`, `run_id`, `pick_date`, `source`, `strategy_counts_json` |
| `candidates` | candidate rows | `id`, `batch_id`, `code`, `strategy`, `pick_date`, `close`, `turnover_n`, `brick_growth`, `extra_json` |
| `review_runs` | review execution metadata | `id`, `run_id`, `candidate_batch_id`, `provider`, `status`, `summary_json` |
| `reviews` | normalized review rows | `id`, `review_run_id`, `code`, `strategy`, `review_key`, `verdict`, `total_score`, `payload_json` |
| `recommendations` | ranked review output | `id`, `review_run_id`, `rank`, `code`, `strategy`, `review_key`, `total_score` |
| `archive_snapshots` | archived daily view metadata | `id`, `pick_date`, `run_id`, `summary_json`, `created_at` |
| `migration_runs` | legacy import attempts | `id`, `source_root`, `status`, `started_at`, `finished_at`, `report_json` |
| `migration_quarantine` | malformed legacy records | `id`, `migration_run_id`, `source_path`, `reason`, `payload_json` |

SQLite constraints:

- `candidates` must keep `(batch_id, code, strategy)` unique.
- `reviews` must keep `(review_run_id, review_key)` unique.
- `review_key` remains derived from `(code, strategy)` unless a future product
  decision changes identity.
- `runs.status` and `job_steps.status` use the same finite state set.
- Generated SQLite files live under `var/db/app.sqlite` and are not committed.

## DuckDB Ownership

DuckDB stores analytical and historical query data.

| Table | Purpose | Key Fields |
| --- | --- | --- |
| `duckdb_schema_versions` | DuckDB migration state | `version`, `applied_at` |
| `market_daily_bars` | imported daily market bars | `trade_date`, `code`, `open`, `high`, `low`, `close`, `volume`, `turnover_n` |
| `candidate_facts` | flattened candidate history | `pick_date`, `run_id`, `batch_id`, `code`, `strategy`, `close`, `turnover_n`, `extra_json` |
| `review_facts` | flattened review history | `pick_date`, `run_id`, `code`, `strategy`, `review_key`, `verdict`, `total_score`, `payload_json` |
| `archive_facts` | archive status rows | `pick_date`, `run_id`, `code`, `strategy`, `status`, `rank`, `chart_artifact_id` |
| `strategy_run_metrics` | per-strategy counts | `pick_date`, `run_id`, `strategy`, `total`, `reviewed`, `recommended`, `unreviewed` |
| `analytics_snapshots` | saved analytical outputs | `id`, `kind`, `created_at`, `params_json`, `result_json` |

DuckDB constraints:

- DuckDB is optimized for reads, scans, and comparisons. Do not use it as the
  transactional source of truth for job state.
- The SQLite row ids can be copied into DuckDB facts as lineage, but analytical
  tables should still be queryable by `pick_date`, `run_id`, `code`, and
  `strategy`.
- DuckDB migrations are versioned SQL files executed by a small Python runner.
- `var/db/analytics.duckdb` is generated local state and is not committed.

## Artifact Layout

Artifacts are generated files that should be traceable from SQLite rows.

```text
var/artifacts/{run_id}/
  logs/
    job.log
    steps/{step_name}.log
  candidates/
    candidates.json
  reviews/
    raw/
    normalized.json
    suggestion.json
  charts/
    {candidate_batch_id}/{code}_day.jpg
    {candidate_batch_id}/{code}_{strategy}_day.jpg
  archive/
    summary.json
    all.json
```

Rules:

- SQLite `artifacts.path` stores relative paths under `var/artifacts/`.
- Legacy chart files under `data/kline/` can be referenced during migration but
  new product runs should write product-owned artifacts.
- New product chart export creates both code-level compatibility artifacts and
  strategy-scoped artifacts keyed by `review_key`. Review provider and archive
  flows should prefer strategy-scoped charts and fall back to code-level charts.
- Large raw provider responses should be artifacts, not SQLite blobs.

## FastAPI Route Groups

All routes are prefixed with `/api`.

| Route Group | Purpose |
| --- | --- |
| `GET /health` | API health and version |
| `GET/PUT /settings` | product settings and provider metadata |
| `GET /strategies` | available strategy definitions and config versions |
| `POST /runs/preselect` | create candidate selection run |
| `POST /runs/review` | create review run for a candidate batch |
| `POST /runs/archive` | create archive snapshot |
| `GET /runs` | list workflow runs |
| `GET /runs/{run_id}` | run summary, status, and linked artifacts |
| `POST /runs/{run_id}/cancel` | request cancellation |
| `GET /jobs/{run_id}/events` | job event stream or polling endpoint |
| `GET /candidates` | candidate query by date/run/strategy/code |
| `GET /candidates/{candidate_id}` | candidate detail and evidence |
| `GET /reviews` | review query by date/run/strategy/status |
| `GET /archive` | archive date list and summary |
| `GET /archive/{pick_date}` | archived rows for a date |
| `GET /artifacts/{artifact_id}` | serve product-owned artifact |
| `GET /analytics/strategy-summary` | strategy/date/run comparison |
| `POST /migrations/import-legacy` | import legacy `data/` into SQLite/DuckDB |
| `GET /migrations/{migration_id}` | migration report and quarantine rows |
| `POST /backups` | create local backup |
| `POST /restore` | restore from local backup |

Pydantic schemas should be defined in `apps/api/stocktrade_api/schemas/` and
covered by API contract tests before frontend implementation relies on them.

## Job Runtime

The job runtime is local-first and intentionally simple.

State set:

- `queued`
- `running`
- `succeeded`
- `failed`
- `cancelling`
- `cancelled`

Run kinds:

- `preselect`
- `review`
- `archive`
- `chart_export`
- `legacy_import`
- `backup`
- `restore`
- `diagnostic`

Job rules:

- Default heavy job concurrency is 1.
- A run owns ordered `job_steps`.
- Each step writes `started_at`, `finished_at`, `status`, `error_json`, and
  relevant artifacts.
- `job_events` are append-only and safe for UI polling.
- Cancellation is cooperative: the API sets `runs.status = cancelling`, and
  step code checks before starting the next expensive operation.
- Failed runs preserve artifacts and logs for diagnosis.
- Resume is allowed only for jobs with explicit checkpoint semantics, such as
  Gemini review. Resume must not rerun completed candidates when
  `skip_existing` applies.

Initial implementation can use FastAPI background tasks or a local worker
thread owned by the API process. Do not introduce Redis, Celery, or distributed
queues unless a future issue proves the local runtime is insufficient.

## Legacy Import and Migration

Legacy `data/` remains the migration source.

Import mapping:

- `data/candidates/candidates_latest.json` and dated candidates import into
  `candidate_batches`, `candidates`, and `candidate_facts`.
- `data/review/{pick_date}/*.json` imports into `review_runs`, `reviews`,
  `recommendations`, and `review_facts`.
- `data/history/{pick_date}/summary.json` and `all.json` import into
  `archive_snapshots`, `archive_facts`, and `strategy_run_metrics`.
- `data/kline/{pick_date}/` chart files import as artifact references or copied
  product artifacts depending on migration mode.
- Malformed records go into `migration_quarantine`.
- `data/trading` is skipped because simulated trading is out of scope.

Migration modes:

- `dry_run`: validates and reports without writing SQLite/DuckDB.
- `import`: writes product state and analytical facts.
- `verify`: compares imported counts and keys against legacy source files.

Rollback:

- Before import, create a backup under `var/backups/{timestamp}/`.
- A failed import leaves its `migration_runs` row and quarantine report.
- Restore replaces `var/db/app.sqlite`, `var/db/analytics.duckdb`, and artifact
  manifest from the selected backup.
- Restore must not mutate legacy `data/`.

## Backup Format

```text
var/backups/{timestamp}/
  manifest.json
  db/
    app.sqlite
    analytics.duckdb
  artifacts_manifest.json
  migration_versions.json
```

`manifest.json` includes product version, git commit if available, created_at,
SQLite schema version, DuckDB schema version, artifact root, and validation
summary.

## API Contract Test Plan

The initial API contract plan has partially landed. Remaining implementation
PRs should keep adding:

- schema tests for every new Pydantic request/response model;
- SQLite migration tests using a temporary database;
- DuckDB migration tests using a temporary database;
- API tests for settings, strategy metadata, analytics summary, and any new
  route groups;
- job lifecycle tests for success, failure, cancellation, and resume when
  runtime semantics change.
